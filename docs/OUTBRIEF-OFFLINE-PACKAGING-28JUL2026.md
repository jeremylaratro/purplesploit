## What was asked

all dependencies vendored, or a static binary.

## What was delivered

Both forms, in one bundle, produced by a reproducible containerised build.

`install.sh` yields two commands: `purplesploit` (the binary) and
`purplesploit-src` (venv + editable source). `--binary-only`, `--check`,
`--prefix` and `PYTHON=` modes are supported.

## Decisions worth knowing

**The build runs entirely inside `kalilinux/kali-rolling`, not on the Fedora
host.** Wheels carry an interpreter ABI tag (`cp313`) and a platform tag, and a
frozen binary links against the glibc of whatever machine froze it. Building on
Fedora would have produced artifacts tagged for Fedora's Python and linked
against Fedora's glibc 2.41. Kali 2026.3 ships Python 3.13.14 and glibc 2.42, so
the container build matches the target exactly.

**`purplesploit/modules` ships as PyInstaller *data*, not just frozen bytecode.**
`Framework.discover_modules()` (`python/purplesploit/core/framework.py:172`)
does an `os.walk` for `.py` files and loads each with
`importlib.util.spec_from_file_location`. Frozen bytecode is invisible to that
walk, so a naive onefile build would start cleanly and load **zero** modules.
The spec ships the tree as data at `purplesploit/modules`, which is precisely
where the framework's default `Path(__file__).parent.parent / "modules"`
resolves under `sys._MEIPASS`.

The corollary: PyInstaller's static analysis never sees those modules' imports,
so every third-party package they touch is declared in `hiddenimports`. The
build asserts the frozen binary discovers the *same module count* as the source
tree, so a partial-import regression fails the build rather than shipping.

**The DB default is relocated when frozen.** `main.py` defaults to
`<project_root>/.data/purplesploit.db` resolved from `__file__`; under onefile
that is the ephemeral `_MEIPASS` dir, so the database would be discarded on every
exit. `entry_frozen.py` sets `PURPLESPLOIT_DB` to
`~/.local/share/purplesploit/purplesploit.db` unless the operator set it. The
`purplesploit-src` launcher uses the same path so both forms share state.

**`requirements-offline.in` is a deliberate superset of `setup.py`.**
`python/setup.py` `install_requires` was missing four packages the source
actually imports — `requests` (6 files), `websockets`, `packaging` (3 files) and
`shodan`. The `.in` file also includes dependencies behind `try/except
ImportError` guards (reporting, OSINT, AI), on the grounds that an offline kit
should be complete rather than silently degrading. `textual` is declared in
`setup.py` but imported nowhere, so it is excluded from the frozen binary.

## Verification

Everything below was run and passed; nothing here is asserted from inspection.

**During the build** (`container-build.sh`, all four gate the build):
1. Wheelhouse installs into a clean venv with `--no-index`.
2. `purplesploit.main` and `Framework` import against those offline deps.
3. The binary answers `--version` and `--help`.
4. The binary discovers 44/44 modules, matching the source tree.

**After the build** (`verify-bundle.sh`, containers with `--network none`):

| Scenario | Result |
|---|---|
| A — bare Kali, **no Python installed**, `./install.sh --binary-only` | PASS — binary runs, 44 modules loaded |
| B — Kali + `python3`/`python3-venv` only, **no pip**, full `./install.sh` | PASS — SHA256SUMS verified, venv built from vendored wheels, imports OK, 44 modules loaded |
| A vs B agreement | PASS — both load 44 modules |

One honest note on process: the first build run **failed** at gate 4. The binary
was fine; the assertion regex looked for `Discovered N modules` while the app
prints `N modules loaded`. The check was corrected to compare against a live
count from the source tree, and the build was re-run clean.

## Known limits (also documented in `INSTALL.md`)

- **PDF reporting needs system libraries.** WeasyPrint is bundled but loads
  Pango/Cairo via `ctypes` at runtime; those `.so` files cannot be vendored into
  a wheel or frozen. The import is guarded, so PDF degrades gracefully and HTML /
  XLSX / DOCX are unaffected. To enable it, stage on the target:
  `apt install libpango-1.0-0 libpangoft2-1.0-0 libharfbuzz0b libcairo2 libffi8`.
- **External pentest tooling is not bundled.** `nmap`, `netexec`, `impacket`,
  `feroxbuster`, `sqlmap`, `wfuzz`, `httpx`, `fzf`, `ripgrep` are shelled out to
  and are Kali packages, out of scope for a Python bundle.
- **AI/OSINT modules are network clients.** `openai`, `anthropic` and `shodan`
  are installed but cannot function air-gapped. All other modules work offline.
- **Architecture and interpreter are fixed** at x86_64 / `cp313`. A different
  arch or Python minor version needs a rebuild.
- **`training/` (583 MB HackTheBox writeups) is excluded** per direction —
  reference material, not runtime data.

## Flagged, not fixed (out of scope)

Two pre-existing issues found while packaging. Neither affects the bundle, and I
did not change application code.

1. **Four inconsistent version strings.** `python/setup.py` says `6.9.1`,
   `main.py --version` says `6.8.1`, the banner in
   `python/purplesploit/ui/display.py:46` says `6.7.0`, and `CHANGELOG.md`'s
   latest entry is `6.9.0`. The bundle is named from `setup.py` (`6.9.1`) as the
   highest and most authoritative. Worth collapsing to a single
   `__version__` source.
2. **`bin/purplesploit-rich` is a dead launcher.** It imports
   `purplesploit.tui.app_interactive`, but there is no `tui` package — the UI
   lives in `purplesploit/ui/`. It will fail with `ModuleNotFoundError` if run.
