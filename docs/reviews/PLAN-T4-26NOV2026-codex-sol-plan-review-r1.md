VERDICT: FIX-FIRST

- **BLOCKER — §4/5, secret handling: parameter previews leak the keys.** `krbtgt_key`/`service_key` as ordinary `ParamSpec`s reach [`params_preview`](/srv/share/dev/purplesploit/.claude/worktrees/t4-kerberos-forging/python/purplesploit/validation/recommend.py:175), which serializes both `value` and `recommended`; pipeline reports include that preview. Safe argv redaction does not protect this path. **Fix:** make secret parameters presence-only in previews, reports, and prompts. Keep capability payloads private and errors fixed-code; test hash, AES, requester-password, cache-path, and exception sentinels across every public serialization.

- **BLOCKER — §4/5, terminal integrity: successful authentication may use an existing ticket.** Ticketer can load an inherited `KRB5CCNAME`; reusing output directories also permits stale artifacts. **Fix:** unset the inherited cache during forging, use a fresh invocation directory, require a newly created, parseable cache with the expected principal/realm/service, and reauthenticate exclusively through that cache using `--use-kcache`, without operator credentials. Delete artifacts after the final consumer, including failure paths. [Ticketer 0.13.1](https://github.com/fortra/impacket/blob/impacket_0_13_1/examples/ticketer.py)

  The proposed generic SMB `[+]` regex is also insufficient: NetExec has an AS-REP-roastability diagnostic logged as success while login returns false. Match the actual cache-backed login line for the bound identity and target. Ordinary authentication must not establish `S_DA`; `Pwn3d` on an arbitrary member proves only that host’s administrative access. [NetExec authentication implementation](https://github.com/Pennyw0rth/NetExec/blob/main/nxc/protocols/smb.py)

- **BLOCKER — §4/5 composition, §8: the engine can report success despite failed reauthentication.** [`_run_one`](/srv/share/dev/purplesploit/.claude/worktrees/t4-kerberos-forging/python/purplesploit/validation/engine/chain_engine.py:352) treats a base-state goal as reached from `complete` plus declared `eff`, without requiring the goal capability. An in-memory reproduction returned `reached=True, escalation=True` with `terminal_fact.ok=False` and no persistence capability. **Fix:** require successful reauthentication before emitting the capability, and require a usable `S_PERSISTENCE` capability in the runtime store before reporting that goal reached. Explicitly test disagreement between `complete`, terminal success, and produced capabilities.

- **HIGH — §4/5, preconditions: the proposed conjunction and acceptance hooks are not implemented contracts.** Preconditions are **OR**, so `{KRBTGT, S0}` makes Diamond/Sapphire directly applicable from the operator seed. The engine calls only `accepts_control`; declaring another `accepts_*` method does nothing automatically. **Fix:** use `chain_pre={KRBTGT}` and explicitly validate the separate live requester credential, or implement conjunction support. Wire key acceptance into consumption/execution: check channel, key format/type, placeholder rejection, and principal/domain binding; composed execution must never substitute an operator key when the produced key is absent or invalid. Defer capability-satisfied key requirements until execution—ordinary required parameters are resolved before DCSYNC has produced anything.

- **HIGH — §§1, 8, graph discovery and H5: the live escalation path needs a front.** Keep DCSYNC `pre={DC_TGT, DA_CREDS}`, `eff={KRBTGT, S_DA}`; GOLDEN `pre=chain_pre={KRBTGT}`, `eff=chain_eff={S_PERSISTENCE}`, with `S_DA` conditional on sufficient privilege evidence. **The distinct goal makes this discoverable already; no special DCSYNC→GOLDEN planning link is needed.** However, `{S0}` cannot start DCSYNC. **Fix:** prove a real `FRONT→DCSYNC→GOLDEN` path from the default seed. Include a given-key control that cannot acquire escalation provenance, and a missing-product control where GOLDEN never runs despite an operator key being available.

- **HIGH — §§1, 4/5, 8, pinned recipes: Sapphire’s declared inputs are insufficient.** Stock 0.13.1’s Sapphire validation requires both signing-key arguments and the requester’s `-password`; AES-only or requester-hash-only input fails. Its request code also passes `-user` directly to `Principal`, so the shown `domain/user` form becomes a multi-component principal. Finally, `-user-id` defaults to 500, which does not identify an arbitrary “plausible DA.” **Fix:** specify and test the carrier’s actual required inputs, pass the requester name separately from the domain, and resolve/bind the forged or impersonated account’s RID. Filter chains lacking those inputs. [Pinned implementation](https://github.com/fortra/impacket/blob/impacket_0_13_1/examples/ticketer.py)

- **HIGH — §4/5, SID resolution: “a SID was present” does not establish the requested domain SID.** Lookupsid’s default lookup can return a member machine’s account-domain SID, despite printing “Domain SID.” **Fix:** bind automatic resolution to the intended domain/DC, select domain-SID lookup explicitly, and parse the complete domain SID. Missing, malformed, ambiguous, or mismatched automatic results remain unknown and establish no capability. Explicit overrides remain available; no fabricated fallback is permitted. [Lookupsid implementation](https://github.com/fortra/impacket/blob/impacket_0_13_1/examples/lookupsid.py)

- **HIGH — §§1, 4/5, Silver effects and persistence semantics: the shared produced-state rule contradicts Silver’s edge.** Silver declares service access but the shared design emits `CAP_CCACHE(state=S_PERSISTENCE)`. The engine drops products outside `eff`; adding global persistence indiscriminately would overstate a service-scoped result. **Fix:** bind Silver’s `chain_pre={cred_for(service_account)}`, declare its service-access effect explicitly, and emit the cache under that effect. Either restrict this tranche to `cifs/<host>` or supply protocol-specific authentication adapters; the SMB predicate cannot validate arbitrary SPNs.

  Keep the distinct Golden persistence goal, but bound its meaning by ticket lifetime and signing-key validity. “Survives credential resets” is too broad: two KRBTGT resets invalidate old Golden tickets. Plain authentication/S4U/U2U can retain `mutating=false`; sessions and audit records do not require AD rollback. [Microsoft KRBTGT guidance](https://techcommunity.microsoft.com/blog/coreinfrastructureandsecurityblog/faqs-from-the-field-on-krbtgt-reset/2367838)

- **HIGH — §7, non-vacuous proofs: the listed negatives do not defeat an implementation that skips forging.** Such an implementation can still authenticate through an existing cache; the non-vulnerable facet RED only checks truth matching. **Fix:** make fake authentication success conditional on the preceding forge creating the exact cache supplied through `KRB5CCNAME`, and assert the consumed signing key and ordered calls. Deliberately replace forging with a no-op and require the positive test to fail. Add stale-cache, wrong-identity, auth-only privilege, placeholder-key, failed-reauthentication, and missing-goal-capability controls, scoring the resulting receipts through the actual harness.
