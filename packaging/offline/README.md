# Offline packaging

Builds a self-contained PurpleSploit bundle for an air-gapped **Kali Linux
x86_64** box. Operator-facing instructions live in `bundle/INSTALL.md`, which is
copied into the bundle; this file is for whoever maintains the build.

## Build

```bash
./packaging/offline/build-offline-bundle.sh
```

Output lands in `build/offline/` (gitignored):

```
purplesploit-offline-<version>-<DDMMMYYYY>/       the bundle
purplesploit-offline-<version>-<DDMMMYYYY>.tar.zst
purplesploit-offline-<version>-<DDMMMYYYY>.tar.zst.sha256
```

Requires `docker` or `podman` (set `CONTAINER=podman` to force one) plus
`rsync`. Network access is needed at *build* time only.

## Why it builds in a container

Wheels carry an interpreter ABI tag (`cp313`) and a platform tag, and a
PyInstaller binary is linked against the glibc of the machine that froze it.
Building on the Fedora host would produce artifacts tagged for Fedora's Python
and linked against Fedora's glibc. The build therefore runs entirely inside
`kalilinux/kali-rolling`, so both match the target.

Rebuild whenever the target's Python minor version changes.

## Layout

| File | Role |
|---|---|
| `Dockerfile.builder` | Kali builder image: python3, toolchain, PyInstaller. |
| `build-offline-bundle.sh` | Host orchestrator. Builds the image, runs the container build, assembles and archives the bundle. |
| `container-build.sh` | Runs inside the container: wheelhouse, offline verification, pinning, PyInstaller build, smoke tests. |
| `requirements-offline.in` | The dependency superset (see below). |
| `purplesploit.spec` | PyInstaller spec. |
| `entry_frozen.py` | Frozen entry point; relocates the DB out of the ephemeral unpack dir. |
| `bundle/install.sh` | Ships inside the bundle. Offline installer. |
| `bundle/INSTALL.md` | Ships inside the bundle. Operator docs. |

## Two coupling points that will bite you

**1. Modules are loaded from `.py` files on disk.**
`Framework.discover_modules()` does an `os.walk` and loads each hit with
`importlib.util.spec_from_file_location`. Frozen bytecode in the PyInstaller
archive is invisible to that walk, so `purplesploit/modules` is shipped as
*data* in `purplesploit.spec`, landing at `$_MEIPASS/purplesploit/modules` —
exactly where the framework's default `Path(__file__).parent.parent / "modules"`
resolves to.

The corollary: PyInstaller's static analysis never sees these modules' imports.
Any third-party package a module imports must be listed in `hiddenimports` in
the spec, or it will be missing from the binary. `container-build.sh` runs a
module-discovery smoke test against the built binary to catch this.

**2. `requirements-offline.in` is a deliberate superset.**
`python/setup.py` was missing `requests`, `websockets`, `packaging` and
`shodan`, all of which are imported by the source. The `.in` file also includes
dependencies whose imports are `try/except ImportError` guarded (reporting,
OSINT, AI), because an offline kit should be complete rather than silently
degrading. `requirements-offline.txt` in the bundle is the resolved pin list,
generated by actually installing the wheelhouse with `--no-index`.

## What the build verifies

`container-build.sh` fails the build if any of these don't hold:

1. The wheelhouse installs into a clean venv with `--no-index` (real proof of
   self-sufficiency, not an assumption).
2. `purplesploit.main` and `Framework` import against those offline-installed
   deps.
3. The frozen binary answers `--version` and `--help`.
4. The frozen binary discovers its modules — the coupling above.

## Known exclusions

`training/` (583 MB of HackTheBox writeups) is excluded from the bundle; it's
reference material, not runtime data. So are `.git/`, `htmlcov/`, caches and
any local `.data/` databases.

The external pentest tooling PurpleSploit shells out to (`nmap`, `netexec`,
`impacket`, `feroxbuster`, `sqlmap`, …) is out of scope — those are Kali
packages, not Python dependencies. WeasyPrint's Pango/Cairo shared libraries
likewise cannot be vendored; see `bundle/INSTALL.md`.
